# خودمیزبانی openGym (Self-hosting)

پروژه openGym از دو کانتینر کوچک (یک وب‌سرور و یک API) به همراه یک پوشه برای ذخیره داده‌های شما تشکیل شده است.  
این راهنما شما را از مرحله «کلون کردن مخزن» تا «استفاده از آن روی گوشی هوشمند از طریق اینترنت» هدایت می‌کند.

## ۱. اجرای محلی (۵ دقیقه)

پیش‌نیازها: نصب [داکر (Docker)](https://docs.docker.com/get-docker/) به همراه پلاگین Compose.

```bash
git clone https://github.com/DuarteSantos8/openGym   # یا آینه https://gitlab.com/DuarteSantos8/opengym — مخزن یکسان است
cd openGym
cp .env.example .env
docker compose pull   # دریافت ایمیج‌های از پیش ساخته شده از ریجستری گیت‌لب (amd64 + arm64؛ همین ایمیج‌ها روی ghcr.io نیز موجودند) — یا رد کنید و از سورس بیلد کنید
docker compose up -d
```

- اولین اجرا، تصاویر و فایل‌های GIF تمرینات (حدود ۱۴۰ مگابایت) را یک‌بار در مسیر `media/img` و `media/gif` دانلود می‌کند.
- آدرس **http://localhost:8080** را در مرورگر باز کرده و یک نمایه با کلید عبور (Passkey) ایجاد کنید.
- ترجیح می‌دهید به جای دانلود ایمیج‌های آماده، از سورس بیلد کنید؟ از دستور `docker compose pull` صرف‌نظر کرده و به جای آن دستور `docker compose up -d --build` را اجرا کنید — در هر دو حالت نیازی به نصب Node به صورت محلی روی هاست نیست.

بررسی سلامت سرویس:

```bash
docker compose ps
curl http://localhost:8080/api/health      # خروجی: {"ok":true,...}
```

مشاهده لاگ‌ها: `docker compose logs -f`. توقف کانتینرها: `docker compose down`.

## ۲. درک الزام کلید عبور (Passkey) — مهم

ورود به openGym از طریق **کلیدهای عبور (Passkeys / WebAuthn)** انجام می‌شود. مرورگرها دو قانون سفت‌وسخت را اعمال می‌کنند:

1. کلیدهای عبور دقیقاً به یک **نام دامنه (Hostname)** مشخص (`RP_ID`) متصل می‌شوند.
2. آن‌ها فقط بر روی بستر امن **HTTPS** کار می‌کنند — با یک استثنا: آدرس `http://localhost`.

بنابراین `http://localhost:8080` روی همان سیستمی که داکر را اجرا می‌کند کار می‌کند، اما **دستگاه دیگر (مثلاً تلفن همراه شما) نمی‌تواند از `http://<your-LAN-ip>:8080` استفاده کند** — این آدرس نه localhost است و نه HTTPS، بنابراین اعلان ایجاد یا ورود با کلید عبور ظاهر نخواهد شد. برای استفاده از openGym از روی گوشی باید یک نام دامنه با گواهی معتبر HTTPS داشته باشید.

(البته همچنان می‌توانید از طریق شبکه محلی در **حالت مهمان (Guest mode)** وارد شوید که داده‌ها را فقط در همان مرورگر ذخیره می‌کند — یا قابلیت **ورود با کلمه عبور** را فعال کنید؛ به [بخش ۴](#ورود-با-کلمه-عبور-اختیاری) مراجعه نمایید.)

اپلیکیشن مستقل موبایل (`docs/MOBILE.fa.md`) در حالت «اتصال به سرور من» این موضوع را به طور کامل دور می‌زند: به جای تشریفات پیچیده کلید عبور (که از داخل WebView اپلیکیشن به دلیل عدم انطباق با دامنه واقعی ناممکن است)، دستگاه از طریق یک کد کوتاه یک‌بارمصرف جفت می‌شود — این کد از مسیر تنظیمات ← "Pair the mobile app" در یک برگه مرورگر لاگین‌شده ایجاد می‌شود — و با یک توکن حامل (Bearer token) که به عنوان هدر `Authorization` ارسال می‌شود کار می‌کند. دو نکته مهم برای کار با API:

- مسیرهای `POST /api/pair/create` (نیازمند نشست فعال) و `POST /api/pair/redeem` (بدون نیاز به نشست) این قابلیت را پیاده‌سازی می‌کنند — به `api/server.js` مراجعه کنید. توکن برگردانده‌شده دقیقاً همان مقدار امضاشده‌ای است که کوکی حمل می‌کند، بنابراین «خروج از همه دستگاه‌ها» آن را نیز باطل می‌کند — و از آنجا که گوشی کلید عبوری برای ورود مجدد ندارد، گوشی‌های جفت‌شده باید **مجدداً جفت شوند**. گوشی این پیام را اعلام کرده و داده‌های خود را تا زمان جفت‌سازی مجدد حفظ می‌کند.
- اعتبار توکن مانند کوکی برابر با `SESSION_DAYS` است اما خودش تمدید می‌شود: فراخوانی `GET /api/me` که برنامه در هر اجرا انجام می‌دهد، در صورتی که بیش از نیمی از عمر توکن سپری شده باشد توکن جدیدی با نسخه نشست جاری حساب صادر می‌کند. ابطال نشست‌ها تحت تأثیر قرار نمی‌گیرد.
- سرور برای هر درخواستی که هدر `Origin` داشته باشد، هدر `Access-Control-Allow-Origin` را برمی‌گرداند تا مبدأ اختصاصی WebView اپلیکیشن بتواند با API ارتباط cross-origin برقرار کند. سرور هرگز `Access-Control-Allow-Credentials` ارسال نمی‌کند، بنابراین مرورگرها نمی‌توانند کوکی شما را از مبدأ دیگری بخوانند.

## ۳. انتشار روی اینترنت با پروتکل HTTPS روی دامنه اختصاصی

> تمایل دارید **بدون** باز کردن پورت‌ها روی اینترنت از HTTPS استفاده کنید — یعنی یک گواهی معتبر روی یک آدرس شبکه محلی (LAN)؟ به [SELF_HOSTING_HTTPS.fa.md](./SELF_HOSTING_HTTPS.fa.md) مراجعه کنید (گواهی وایلدکارد از طریق چالش DNS به همراه Caddy).

سرویس openGym را پشت ابزاری قرار دهید که TLS را برای نام دامنه‌ای که در اختیار دارید خاتمه می‌دهد، سپس ترافیک را به کانتینر `web` هدایت کنید:

### گزینه الف — استفاده از Cloudflare Tunnel (بدون نیاز به باز کردن پورت در مودم)

1. یک تونل بسازید و مسیر `gym.example.com` را به `http://<docker-host>:8080` هدایت کنید.
2. کلودفلر به‌صورت خودکار گواهی امنیتی HTTPS را فراهم می‌کند.

### گزینه ب — استفاده از Caddy (Let's Encrypt کاملاً خودکار)

```caddy
gym.example.com {
    reverse_proxy localhost:8080
}
```

### گزینه ج — استفاده از Traefik / Nginx / Nginx Proxy Manager

مسیر `gym.example.com` (HTTPS) را به `web:80` (یا `<docker-host>:8080`) روت کنید. هر پروکسی معکوسی کار می‌کند — openGym فقط نیاز دارد مرورگر از طریق `https://gym.example.com` به آن دسترسی پیدا کند. اگر آن پروکسی حجم بدنه درخواست‌ها را محدود می‌کند (مثلاً در nginx به طور پیش‌فرض ۱ مگابایت است)، حداقل ۵ مگابایت را برای مسیر `/api/` مجاز کنید — اپلیکیشن کل تاریخچه خود را در یک درخواست PUT همگام‌سازی می‌کند؛ ایمیج کانتینر وب پیش‌فرض ۵ مگابایت را مجاز کرده است. تصاویر و ویدیوهایی که کاربران به تمرینات سفارشی ضمیمه می‌کنند نیاز به فضا و زمان بیشتری در مسیر `/api/media/` دارند — به [تصاویر و ویدیوهای تمرینات سفارشی](#تصاویر-و-ویدیوهای-تمرینات-سفارشی) مراجعه کنید.

سپس دامنه خود را در فایل `.env` تنظیم کرده و سرویس را مجدداً راه‌اندازی کنید:

```bash
# .env
RP_ID=gym.example.com
ORIGIN=https://gym.example.com
WEB_PORT=8080
RP_NAME=openGym
```

```bash
docker compose up -d
```

سایت `https://gym.example.com` را باز کنید، نمایه خود را بسازید و آن را به صفحه اصلی گوشی اضافه کنید (در iOS: دکمه Share ← Add to Home Screen؛ در Android: منوی سه نقطه ⋮ ← Add to Home screen).

> تغییر `RP_ID` در آینده، کلیدهای عبور قبلی را باطل می‌کند (زیرا آن‌ها به هاست قبلی گره خورده بودند). قبل از ثبت‌نام کاربران، دامنه نهایی خود را انتخاب کنید.

## ۴. مدیریت چند کاربر

هر فردی که بتواند این آدرس را باز کند می‌تواند نمایه اختصاصی خود را بسازد — داده‌های هر کاربر کاملاً مجزا و ایزوله است. این حالت پیش‌فرض است: ثبت‌نام آزاد، بدون نیاز به مدیر.

اگر ترجیح می‌دهید ورودی‌ها را کنترل کنید، سه تنظیم اختیاری در `.env` این کار را انجام می‌دهند:

```bash
ADMIN_UIDS=youruserid      # شناسه‌های کاربری که با کاما جدا شده‌اند؛ این افراد به پنل ادمین دسترسی دارند
INVITE_ONLY=1              # ثبت نمایه‌های جدید نیازمند کد دعوت خواهد بود
ALLOW_GUEST=0              # حذف دکمه "ورود بدون حساب (Continue without account)"
```

ابتدا نمایه کلید عبور خود را بسازید، سپس شناسه خود را از مسیر **تنظیمات ← حساب کاربری ← Account ID** کپی کنید (روی آن تپ کنید تا کپی شود؛ در `./data/db.json` زیر `users[].id` نیز موجود است) و آن را در `ADMIN_UIDS` قرار دهید. لینک **داشبورد مدیریت (Admin dashboard)** در تنظیمات برای شما نمایان خواهد شد: چه کسی هم‌اکنون در حال تمرین است، سابقه تمرینات و وزن هر کاربر، امکان غیرفعال کردن حساب کاربری (خروج از همه جا و مسدود شدن تا فعال‌سازی مجدد توسط شما) و — با فعال بودن `INVITE_ONLY=1` — تولید و ابطال کدهای دعوت. با فعال‌سازی کد دعوت، حساب‌های موجود به فعالیت خود ادامه می‌دهند. دسترسی مدیر توسط کلید عبور شما تأیید می‌شود و در سمت سرور کنترل می‌گردد، بنابراین نیازی به ورود جداگانه ندارد.

### زبان پیش‌فرض (Default Language)

سروری که کاربران آن زبان مشترکی دارند می‌تواند از ابتدا همه را با آن زبان شروع کند:

```bash
DEFAULT_LANG=fa            # هر کدی از مسیر Settings → Language: fa, en, de, es, fr, pt-BR, …
```

صفحات ورود و ساخت نمایه با این زبان باز می‌شوند، و همین‌طور نمایه‌هایی که هرگز زبانی در بخش تنظیمات انتخاب نکرده‌اند. انتخاب دستی هر فرد همواره اولویت دارد و نمایه‌هایی که قبل از این تنظیم ساخته شده‌اند زبان خود را حفظ می‌کنند. بدون تنظیم `DEFAULT_LANG`، کاربر با زبان مرورگر خود (در صورت وجود ترجمه) و در غیر این صورت با انگلیسی وارد می‌شود. اپلیکیشن موبایل در حالت محلی سروری برای سؤال کردن ندارد و تحت تأثیر این تنظیم نیست.

### لاگ فعالیت‌ها (The Activity Log)

داشبورد ادمین همچنین یک **لاگ فعالیت (Audit Log)** را ثبت می‌کند: ورودها، خروج‌ها، تلاش‌های ناموفق، ثبت‌نام‌های رد شده و تمام اقدامات ادمین (مسدودسازی حساب، ساخت یا لغو کد دعوت). این فایل در `./data/audit.log` به صورت یک آبجکت JSON در هر خط ذخیره می‌شود، بنابراین دستوراتی مانند `tail -f data/audit.log` و `jq` مستقیماً روی آن کار می‌کنند.

این قابلیت به طور پیش‌فرض روشن است و ۵۰۰۰ رویداد آخر یا ۹۰ روز گذشته را نگه می‌دارد (`AUDIT_LOG=0` آن را خاموش می‌کند؛ متغیرهای `AUDIT_MAX` و `AUDIT_DAYS` این سقف‌ها را تغییر می‌دهند). **آدرس‌های IP ثبت نمی‌شوند** مگر اینکه متغیر `AUDIT_IP=net` (ثبت شبکه، مثلاً `203.0.113.0/24`) یا `AUDIT_IP=full` را تنظیم کنید. مشخصات مرورگر (User-agent) و شناسه کلید عبور تلاش‌های ناموفق هرگز ثبت نمی‌شوند.

**کاربران مهمان هرگز در لاگ ظاهر نمی‌شوند** زیرا حالت مهمان هرگز با سرور ارتباط برقرار نمی‌کند. همچنین **حساب مسدودشده فعالیتی ندارد**: کاربر مسدود در بررسی نشست رد می‌شود، بنابراین تنها ورودی‌های او تلاش‌های ناموفق برای ورود است.

### ورود با کلمه عبور (اختیاری)

کلیدهای عبور گزینه پیش‌فرض و پیشنهادی هستند. اما برخی کاربران ممکن است نتوانند از آن‌ها استفاده کنند: مرورگری در آدرس متنی `http://` در شبکه محلی، سیستم‌هایی که فقط کلید سخت‌افزاری ارائه می‌دهند، یا عدم امکان انتقال کلید عبور از گوشی به کامپیوتر. برای این افراد امکان ورود با نام کاربری و رمز عبور به صورت اختیاری تعبیه شده است:

```bash
PASSWORD_LOGIN=1
```

با فعال شدن این گزینه:

- صفحه ورود گزینه **Sign in with password** را نمایش می‌دهد و بخش ایجاد نمایه می‌تواند به جای کلید عبور از رمز عبور استفاده کند. با فعال بودن `INVITE_ONLY=1` کد دعوت درخواست می‌شود.
- در مسیر تنظیمات ← حساب کاربری ردیف **Password** اضافه می‌شود. هیچ کاربری تا زمانی که رمزی تنظیم نکند رمز نخواهد داشت. تنظیم رمز عبور اولیه نیازمند تأیید با کلید عبور است؛ تغییر آن نیازمند رمز فعلی (یا کلید عبور در صورت فراموشی) است. هر تغییری کاربر را از تمام دستگاه‌های دیگر خارج می‌کند.
- ورود با **نام نمایه** (بزرگی و کوچکی حروف و فاصله‌های اطراف تأثیری ندارد) و رمز عبور انجام می‌شود. دو نمایه دارای رمز عبور نمی‌توانند نام یکسانی داشته باشند.
- امکان ورود اختیاری با **آدرس ایمیل** به جای نام کاربری.
- تا زمانی که رمز عبور تنها راه ورود باشد، نمی‌توان آن را حذف کرد.

**غیرفعال‌سازی مجدد آن** تمامی مسیرهای رمز عبور را می‌بندد و رمز قبلی نیز برای تأیید عملیات‌ها دیگر اعتباری نخواهد داشت. قبل از خاموش کردن این قابلیت، از کاربرانی که تنها رمز عبور دارند بخواهید یک کلید عبور به حساب خود اضافه کنند.

**ورود با ایمیل:** در تنظیمات ← حساب کاربری ردیف **Sign-in e-mail** قرار دارد. پروژه openGym فاقد میل‌سرور است و **هرگز پیامی ارسال نمی‌کند**: هیچ ایمیل فعال‌سازی یا بازیابی رمزی وجود ندارد — بازیابی رمز عبور از طریق کد ادمین انجام می‌شود. ایمیل تنها نام مستعار دومی برای اشاره به حساب کاربری است.

**بازیابی رمز عبور:** در پنل مدیریت کاربر را باز کرده و **Reset password** را انتخاب کنید. یک کد یک‌بارمصرف مانند `K7WQ-2MZP-4HXA` به شما داده می‌شود تا حضوری یا با پیام به کاربر برسانید: این کد یک بار نمایش داده می‌شود، یک بار کار می‌کند، ۲۴ ساعت معتبر است و فقط هش آن در سرور نگهداری می‌شود. صدور آن رمز فعلی کاربر را حذف کرده و او را از همه جا خارج می‌کند. کاربر نام خود، کد و رمز جدید را در بخش مربوطه وارد می‌کند.

**محدودیت‌های امنیتی رمز عبور:**
- هش‌ها با الگوریتم قدرتمند scrypt ذخیره می‌شوند.
- ۵ بار تلاش اشتباه برای یک حساب، ورود رمز آن حساب را به مدت ۱ دقیقه متوقف می‌کند که تا یک ساعت قابل افزایش است. ۲۰ بار تلاش اشتباه از یک آدرس IP، آن آدرس را به مدت ۳۰ ثانیه (قابل افزایش تا ۱۵ دقیقه) مسدود می‌سازد. کلیدهای عبور مشمول این محدودیت‌ها نمی‌شوند.
- طول رمز عبور باید بین ۱۰ تا ۲۵۶ کاراکتر باشد و نباید در لیست رمزهای ساده رایج باشد.

## ۵. ادغام در استک و زیرساخت موجود

مانیفست‌های نمونه کوبرنتیز در پوشه `kubernetes/` موجود است و در [SELF_HOSTING_KUBERNETES.fa.md](SELF_HOSTING_KUBERNETES.fa.md) تشریح شده است.

تنظیمات پورت و پراکسی در `.env`:

```bash
WEB_PORT=8080              # پورتی که روی هاست باز می‌شود
NGINX_PORT=80              # پورت داخلی وب‌کانتینر
BACKEND=api                # نام سرویس API که درخواست‌های /api به آن فوروارد می‌شوند
PORT=3000                  # پورت داخلی سرویس API
RESOLVER=127.0.0.11        # آدرس DNS سرور داکر برای بازتطبیق IPها
BASE_PATH=                 # در صورت اجرا ذیل یک زیرمسیر، مثلاً /gym
SESSION_DAYS=90            # مدت زمان اعتبار نشست ورود (به روز)
```

### سرویس‌دهی ذیل یک زیرمسیر (Subpath)

اگر می‌خواهید openGym در آدرسی مانند `https://example.com/gym/` اجرا شود:
- اگر پروکسی شما پیشوند را حذف می‌کند (مانند `handle_path` در Caddy): نیازی به تغییر خاصی نیست.
- اگر پروکسی پیشوند را مستقیماً عبور می‌دهد: مقدار `BASE_PATH=/gym` را در `.env` تنظیم کنید.
در هر دو حالت مقادیر `ORIGIN` و `RP_ID` باید به آدرس اصلی در نوار آدرس مرورگر اشاره کنند (`ORIGIN=https://example.com` و `RP_ID=example.com`).

### تصاویر و ویدیوهای تمرینات سفارشی

هر کاربر لاگین‌شده می‌تواند یک عکس، GIF یا ویدیوی کوتاه به تمرین دست‌ساز خود اضافه کند و تا ۶ عکس یا ویدیو به تمرین ثبت‌شده ضمیمه کند. فایل‌ها در `./data/uploads/<profile id>/` با هش SHA-256 ذخیره می‌شوند. متغیرهای تنظیم حجم و سهمیه در `.env`:

| متغیر | مقدار پیش‌فرض | توضیحات |
|---|---|---|
| `MEDIA_UPLOADS` | `1` | با تنظیم `0` مسیرهای آپلود بسته شده و تنها فیلد لینک فعال می‌ماند |
| `MEDIA_QUOTA_MB` | `200` | سقف فضا برای هر نمایه (مگابایت)؛ `0` یعنی نامحدود |
| `MEDIA_IMAGE_MAX_MB` | `2` | حداکثر حجم هر تصویر (برنامه آن را به ۱۶۰۰ پیکسل فشرده می‌کند) |
| `MEDIA_GIF_MAX_MB` | `8` | حداکثر حجم فایل گیف متحرک |
| `MEDIA_VIDEO_MAX_MB` | `40` | حداکثر حجم ویدیو |
| `MEDIA_VIDEO_MAX_SEC` | `60` | حداکثر طول ویدیو (ثانیه) |
| `MEDIA_GC_GRACE_DAYS` | `14` | مهلت نگهداری فایلی که دیگر در هیچ کجای برنامه استفاده نمی‌شود |
| `MEDIA_UPLOADS_PER_HOUR` | `600` | حداکثر تعداد آپلود در ساعت برای هر کاربر |
| `MEDIA_MIN_FREE_MB` | `512` | در صورت کاهش فضای خالی دیسک از این مقدار، آپلودها متوقف می‌شوند |
| `MEDIA_UPLOAD_MAX` | `48m` | محدودیت بدنه وب‌کانتینر برای `/api/media/` در نحو nginx |

**تنظیمات پروکسی معکوس:**
- حجم درخواست (`client_max_body_size` در nginx): حداقل به میزان `MEDIA_VIDEO_MAX_MB` برای مسیر `/api/media/`.
- مهلت زمانی (Timeout): یک ویدیوی ۴۰ مگابایتی روی اینترنت کند ممکن است دقایقی طول بکشد؛ تنظیمات تایم‌اوت پراکسی را در صورت لزوم افزایش دهید (مثلاً ۶۰۰ ثانیه).
- پالیسی CSP: هدر Content-Security-Policy باید دسترسی `blob:` را در `img-src` و `media-src` مجاز بداند.

## ۶. پشتیبان‌گیری (Backups)

تمام داده‌های حیاتی در پوشه `./data` قرار دارند:

```bash
tar czf opengym-backup-$(date +%F).tar.gz data/
```

این آرشیو شامل تمامی نمایه‌ها، کلیدهای عبور، تاریخچه تمرینات و در صورت فعال بودن، فایل لاگ `audit.log` است. برای بازیابی کافی است این آرشیو را در پوشه پروژه استخراج کنید. (کاربران می‌توانند از داده‌های خود به صورت JSON از منوی تنظیمات خروجی بگیرند.)

اگر نمی‌خواهید ویدیوها و تصاویر آپلودشده در آرشیو بکاپ قرار گیرند (جهت کاهش حجم بکاپ):

```bash
tar czf opengym-backup-$(date +%F).tar.gz --exclude=data/uploads data/
```

در صورت بازیابی بدون فایل‌های آپلودی، تمامی نمایه‌ها سالم خواهند بود و برای رسانه‌های مفقود یک نشانگر موقت نمایش داده می‌شود تا زمانی که یکی از دستگاه‌های کاربر (که نسخه محلی را دارد) آن را دوباره آپلود کند.

توجه: اگر مربی هوش مصنوعی را با ارائه‌دهنده Codex فعال کرده‌اید، پوشه `./coach-auth` به عمد خارج از `./data` قرار گرفته است تا توکن‌های رفرش زنده در فایل‌های پشتیبان قرار نگیرند. اگر این پوشه از بین رفت، کافی است مجدداً وارد حساب آن ارائه‌دهنده شوید.

کلیدهای API ارائه‌دهندگان HTTPS (مثل Anthropic، OpenAI، Gemini و ...) به صورت رمزگذاری‌شده درون `./data/coach.json` نگهداری می‌شوند و بدون فایل `./data/secret` قابل خواندن نیستند.

## ۷. اعلان‌ها (Notifications)

سامانه openGym می‌تواند دو نوع اعلان را به گوشی یا دسکتاپ ارسال کند: پایان زمان استراحت بین ست‌ها، و یادآور روز تمرینی که هنوز تمرینی در آن ثبت نشده است. این مورد را در مسیر **تنظیمات ← اعلان‌ها (Notifications)** فعال کنید (نیازمند نمایه ثبت‌شده با کلید عبور و بستر HTTPS است).

نیازی به تنظیم خاصی در سمت سرور یا تنظیم منطقه زمانی نیست: کلیدهای VAPID در اولین اجرا تولید شده و در `./data/vapid.json` ذخیره می‌شوند، و مرورگر کاربر منطقه زمانی محلی خود را هنگام فعال کردن یادآور به سرور گزارش می‌دهد.

پشتیبانی: در تمام مرورگرهای دسکتاپ، کروم اندروید، و در iOS تنها در حالتی که وب‌اپلیکیشن به **صفحه اصلی (Home Screen)** اضافه شده باشد (سافاری در برگه عادی از Web Push پشتیبانی نمی‌کند). نسخه APK اندروید برای یادآور روزانه از اعلان محلی و برای زمان استراحت از یک Foreground Service محلی استفاده می‌کند.

روشن ماندن صفحه (**Keep screen awake**) در حین تمرین نیز نیازمند HTTPS یا localhost است زیرا API قفل بیداری (Wake Lock) تنها در بسترهای امن کار می‌کند.

## ۸. به‌روزرسانی

اگر از ایمیج‌های آماده استفاده می‌کنید:

```bash
git pull                    # دریافت تغییرات فایل‌های compose و کانفیگ
docker compose pull

```

اگر از سورس بیلد کرده‌اید:


## رفع مشکل عدم کارکرد کلید عبور علیرغم صحیح به نظر رسیدن `RP_ID`

این مورد شایع‌ترین سؤال پشتیبانی است. این مراحل را به ترتیب بررسی کنید:

**۱. از سرور بپرسید چه مقداری را لود کرده است:**
```bash
docker compose logs api | grep 'gym-api on'
# خروجی نمونه: gym-api on :3000 (rpID=gym.example.com, origin=https://gym.example.com)
```
اگر این مقادیر با `.env` مغایرت دارند، کانتینر هنوز محیط قدیمی را اجرا می‌کند. دستور `docker compose restart` متغیرهای محیطی را مجدداً نمی‌خواند — حتماً از `docker compose up -d` استفاده کنید.

**۲. ساختار دقیق هر مقدار را بررسی کنید:**

| | فرمت صحیح | فرمت اشتباه |
|---|---|---|
| `RP_ID` | `gym.example.com` | `https://gym.example.com`, `gym.example.com:8080`, `gym.example.com/` |
| `ORIGIN` | `https://gym.example.com` | `gym.example.com`, `https://gym.example.com/` |

متغیر `RP_ID` نام خالص هاست است: بدون پروتکل، بدون پورت، بدون اسلش انتهایی. متغیر `ORIGIN` مبدأ کامل *همراه با* پروتکل و *بدون* اسلش انتهایی است.

**۳. پشت یک پروکسی یا تونل، از دامنه عمومی استفاده کنید:**
با کلودفلر تانل، Caddy، Nginx یا Traefik، مرورگر فقط دامنه عمومی را می‌بیند — بنابراین هر دو متغیر باید نام عمومی باشند، نه نام کانتینر یا IP محلی.

**۴. پیشوند `www.` یک هاست کاملاً متفاوت است:**
کلید عبور ثبت‌شده روی `gym.example.com` روی `www.gym.example.com` کار نخواهد کرد. یکی را انتخاب کرده و دیگری را به آن ریدایرکت کنید.

**۵. تغییر نام دامنه کلیدهای عبور قبلی را باطل می‌کند.**

## کدام ارائه‌دهندگان کلید عبور کار می‌کنند؟

پروژه openGym درخواست استاندارد کلید عبور را ثبت می‌کند و نوع ابزار ذخیره‌کننده توسط سیستم‌عامل و مرورگر تعیین می‌شود:
- **اندروید ۱۴ و جدیدتر:** برنامه‌های مدیریت رمز عبور مانند Bitwarden، 1Password، Proton Pass و Google Password Manager به طور کامل پشتیبانی می‌شوند (در بخش Passwords & accounts فعال شوند). در اندروید ۱۳ و قبل‌تر تنها Google Password Manager قابل استفاده است.
- **ویندوز ۱۰ و فایرفاکس:** فایرفاکس در ویندوز ۱۰ گزینه اسکن QR با موبایل ندارد (ویندوز ۱۱ این قابلیت را اضافه کرده است). می‌توانید از کروم یا اج استفاده کنید، یا از طریق Windows Hello روی همان پی‌سی با استفاده از گزینه **Add another device** یک کلید محلی بسازید.
- **آیا یک نمایه می‌تواند چند کلید عبور داشته باشد؟** بله. از طریق **تنظیمات ← حساب کاربری ← Passkeys** می‌توان کلیدهای جدیدی اضافه یا حذف کرد. برای اتصال دستگاه دوم، مسیر **Settings → Account → Add another device** یک کد ۱۲ رقمی و QR کد تولید می‌کند که دستگاه دوم با وارد کردن آن در صفحه لاگین کلید عبور اختصاصی خود را می‌سازد.
- **اگر کلید عبورم را گم کردم چه کنم؟** اگر کلید دومی دارید با آن وارد شوید. در غیر این صورت، در صورت فعال بودن `PASSWORD_LOGIN=1` مدیر سیستم می‌تواند یک کد ریست صادر کند، و در غیر این صورت تنها راه استفاده از فایل پشتیبان JSON است. به همین دلیل توصیه می‌شود همیشه یک کلید عبور پشتیبان برای حساب خود بسازید.

## جدول عیب‌یابی (Troubleshooting)

| مشکل | راه‌حل |
|---|---|
| اعلان کلید عبور روی گوشی من نمایش داده نمی‌شود | شما در آدرس `http://` یا با آدرس IP متصل شده‌اید، نه با HTTPS. دامنه معتبر با گواهی HTTPS تنظیم کنید (بخش ۳). |
| پیام خطای "verification failed" در هنگام ورود | مقادیر `RP_ID` یا `ORIGIN` با نشانی موجود در نوار آدرس مرورگر همخوانی ندارند. |
| رسانه‌ها دانلود نشدند | دستور `docker compose logs media` را اجرا کنید. مجدداً دستور `docker compose up -d` یا `./scripts/fetch-media.sh` را اجرا نمایید. |
| پورت 8080 اشغال است | مقدار `WEB_PORT=9090` را در `.env` قرار دهید. |
| عکس یا ویدیو آپلود نمی‌شود ("refused as too large" یا در میانه راه قطع می‌شود) | پروکسی مقابل سرور حجم بدنه را محدود کرده یا درخواست را قطع می‌کند؛ به بخش [تصاویر و ویدیوها](#تصاویر-و-ویدیوهای-تمرینات-سفارشی) مراجعه کنید. |
| گزینه اعلان‌ها در تنظیمات وجود ندارد | نیازمند ورود به یک نمایه با کلید عبور و بستر HTTPS (یا localhost) است؛ حالت مهمان یا ارتباط ساده HTTP این قابلیت را ندارد. |
| پیام "Your server no longer accepts this phone" | سرور خطای 401 داده است. دلایل: خروج از همه جا، مسدود شدن حساب، حذف فایل `data/secret`، یا رد هدر `Authorization: Bearer` توسط پروکسی. داده‌های دستگاه محفوظ است؛ گوشی را مجدداً جفت کنید تا اطلاعات ادغام شوند. |
| پیام سرور با کدی غیر از openGym پاسخ داد (HTTP 200) | چیزی به غیر از API به مسیر `/api/*` پاسخ داده است (مثل صفحه لاگین پراکسی یا صفحه HTML پیش‌فرض). تمام پاسخ‌های API باید JSON باشند؛ ترافیک `/api/*` را مستقیماً به کانتینر API برسانید. |
| دانلود ایمیج با خطای "denied" یا "unauthorized" روبرو می‌شود | ایمیج‌ها را به صورت محلی از روی سورس بسازید (`docker compose up -d --build`). |
| تصاویر حین باز بودن برنامه تمرینی خالی هستند | در ایمیج‌های فعلی رفع شده است. |
| یک حرکت تمرینی در حالت آفلاین به جای انیمیشن یک کادر ساده نشان می‌دهد | وب‌اپلیکیشن نصب‌شده روی صفحه اصلی تصاویر تمرینات برنامه جاری شما را در پس‌زمینه دانلود می‌کند (تا ۱۵۰ مگابایت). تمرینی خارج از برنامه که تا کنون به صورت آنلاین باز نشده باشد در حالت آفلاین نمایشی نخواهد داشت. |

### متغیرهای `VITE_IMG_BASE` و `VITE_GIF_BASE` مربوط به زمان بیلد هستند نه زمان اجرا

این دو متغیر هنگام **کامپایل** فرانت‌اند توسط Vite خوانده می‌شوند و مقادیر آن‌ها درون باندل جاوااسکریپت قرار می‌گیرد. قرار دادن آن‌ها در فایل `.env` در کنار `docker compose` هیچ تأثیری روی ایمیج از پیش بیلد شده نخواهد داشت.  
این متغیرها تنها در صورتی کاربرد دارند که خودتان فرانت‌اند را بیلد کنید (`docker compose up -d --build` یا اجرای `npm run build` با متغیرهای صادرشده). اگر نیاز به تغییر مسیر مدیا روی ایمیج آماده دارید، این کار را در پروکسی معکوس خود انجام دهید.
